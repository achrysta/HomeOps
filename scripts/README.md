# Автопрогон инцидентов

Из корня проекта, на хосте нужен только Docker Compose:

```text
docker compose --profile tools run --rm --build incident-regression
```

Один стенд или план без создания кластера:

```text
docker compose --profile tools run --rm --build incident-regression k8s-probes
docker compose --profile tools run --rm --build incident-regression --plan
```

Совместимость namespace-стендов экзамена (Gateway API + оператор) — отдельный режим:

```text
docker compose --profile tools run --rm --build incident-regression --exam-compatibility
```

Он готовит два стенда последовательно, проверяет полный результат каждого и сохранность второго после teardown первого — в обоих направлениях. Используются тот же отдельный кластер, копии и DASHBOARD_URL=off; это не попытка экзамена и не вызов сервиса labs.

«Финал» (storm + operator + storage):

```text
docker compose --profile tools run --rm --no-deps incident-regression --exam-final-compatibility
```

Три стенда подготавливаются последовательно в копиях, проверяются вместе, затем после teardown каждого проверяются оба соседа (9 полных отчётов). Для обоих режимов совместимости допустим только фиксированный состав. После exclusive-стенда runner создаёт новый `homeops-regression` перед следующим namespace-стендом; рабочий кластер не затрагивается.

На Windows запускайте из проекта в WSL2, как остальные стенды. ARM64 и AMD64 используют те же мультиархитектурные образы. Результаты проверки Windows 11 / WSL2 / amd64 и ограничения холодного кэша — в [WINDOWS.md](../WINDOWS.md).

## Контрольные состояния

Каталог содержит **62 фиксированных стенда и 311 этапов**: namespace/nodeAccess Kubernetes, Linux, Compose/CI и MLOps, включая 4 GPU-стенда (25 этапов) и agent-loop/airflow-retrain/kserve-isvc (30 этапов). Новые стенды автоматически не включаются; план всех этапов — `--plan`.

У каждого — исходная поломка, осмысленное частичное и полное исправление. После полного исправления идут отрицательные этапы `bypass-*`: нарушения ограничений обязаны оставаться красными. У последовательных проверок DNS/SSH частичный шаг может оставить весь отчёт красным: следующая проверка ещё заблокирована предыдущей.

| Стенд | Исходное | Частично исправленное | Исправленное |
| --- | --- | --- | --- |
| `k8s-crashloop` | Запуск, стабильность и конфигурация красные | Команда и переменная окружения исправлены, лимит памяти снят: только `limits` красная | Лимит 128Mi, все четыре проверки зелёные |
| `k8s-probes` | Стабильность и выкатка красные | Liveness исправлена, readiness пропускает запросы при загрузке: стабильность зелёная, `rollout` красная | Readiness проверяет готовность модели, обе проверки зелёные |
| `k8s-service-endpoints` | Селектор/порт каталога и DNS витрины сломаны | Каталог доступен, витрина ещё ждёт DNS в своём namespace | FQDN в init-контейнере и приложении; пять зелёных проверок |
| `linux-systemd-unit` | Неверный User, права, disabled, Restart=no | Запущен от reportsvc, автозапуск и восстановление ещё сломаны | Enabled и Restart=always, четыре зелёные проверки |
| `docker-oom-healthcheck` | OOM и curl, которого нет в образе | Кэш 40 МБ в лимите 96 МБ; healthcheck ещё сломан, API не стартовал | Healthcheck через Python, API работает, воркер стабилен |
| `pg-wal-retention` | Выведенный из эксплуатации слот держит старый WAL | Слот удалён, сегмент ещё на диске | Контрольная точка освобождает сегмент, LSN аварийного слота сохранён |
| `pg-pitr` | Копия проиграла WAL до конца и повторила удаление | Данные восстановлены, копия на паузе | Копия вышла из recovery, исходный экземпляр не изменён |
| `pg-sync-replica` | Коммиты ждут выведенную standby1 | Список включает standby2, но она подключена как walreceiver — всё ещё красно | standby2 под своим именем подтверждает коммиты, зависшие чеки проведены по одному разу |
| `pg-logical-conflict` | Подписка встала на ручной строке 4 | Строка 4 убрана, поток дошёл до ручной строки 6 — всё ещё красно | Ручные правки убраны, витрина совпадает с биллингом, проба доходит |
| `redis-sentinel-failover` | Ни одна реплика не пригодна для повышения | redis-2 пригодна, после переключения приложение получает READONLY | Приложение находит мастер через Sentinel, учения проходят дважды |
| `redis-eviction` | `noeviction` и вечные карточки: запись отклоняется | `volatile-lru` и очистка кэша, карточки ещё без TTL | TTL 5 минут: нагрузка вдвое сверх лимита вытесняет кэш, задания целы |
| `train-serve-skew` | Порядок, единицы и пропуски отличаются | Порядок/масштаб исправлены, пропуски ещё нули | Заполнение средним из артефакта; полные данные и пропуски совпадают |

Код `verify` 1 нормален для исходного и частичного состояния. Успех автопрогона означает совпадение **каждой проверки** с ожиданием, включая ожидаемые ошибки. Неожиданно зелёная поломка, пропавший/дублированный id, пустое сообщение, несогласованный `passed`, неверный код выхода или отсутствие свежего отчёта делают прогон красным.

## Изоляция

- Исходный `incidents/` доступен runner только для чтения. Работа идёт в копиях; правимые файлы копии восстанавливаются из `.original/`, текущие правки пользователя сохраняются.
- Кластер — `homeops-regression`, kubeconfig — отдельный том `homeops-regression-kubeconfig`, образ — `homeops-regression-tools:1`, compose-проекты начинаются с `homeops-regression-`. Рабочий `homeops`, его том и проекты `inc-*` не используются. Стандартная Docker-сеть `kind` может быть общей, Kubernetes-кластеры отдельные.
- `DASHBOARD_URL=off` установлен в override каждого сервиса и явно для `verify/reset`. `data/` не примонтирован, API дашборда не вызывается.
- Контейнер `homeops-regression-lock` служит глобальной арендой Docker, включая второй checkout. Другой прогон не стартует. Существующие тестовые узлы/том также вызывают отказ: их нельзя автоматически удалять или переиспользовать.
- Обычный Compose нормализуется с включёнными profiles: все host-порты и container_name удаляются, bind-пути перенаправляются в копию, именованные тома и сети получают префикс тестового проекта. Внешние тома/сети и bind вне копии отклоняются; исключение — `/sys/fs/cgroup` учебного systemd-сервера. Сервер проверяется через `exec server verify` после подготовки; обычные стенды — через одноразовый `verify`.
- Для nodeAccess: строго по одному, `cluster down → up → prepare <id> → рабочее место`; после стенда кластер удаляется. Независимый обход ручного обновления kubeadm также начинает со свежего кластера. Имена `homeops-worker`/`homeops-control-plane` в проверках и манифестах заменяются только внутри тестовой копии, включая `.original`; исходники и рабочий `homeops` не меняются.
- Если локального `homeops-k8s-upgrade:v1.37.1` нет, сценарий помечается `skipped`; образ не собирается и не скачивается. Пропуск не делает summary зелёным. Кэш образов не удаляется.
- `llm-context` использует существующий CPU-пресет 0.5B в собственном томе моделей: качество ответов проверка не оценивает. Том и модель пользователя не используются.

Runner, как сервис labs, имеет сокет Docker; это инструмент разработчика с фиксированными контрольными сценариями, без публичного API и портов.

Служебный контейнер kind запускается с `network_mode: none`: управление идёт через Docker-сокет и `docker exec`, отдельная служебная сеть не создаётся.

## Отчёт и очистка

В `regression-runs/<дата-и-id>/` сохраняются `commands.log`, JSON-отчёты этапов и итоговый `summary.json` формата `homeops-incident-regression`. Эти отчёты предназначены для разработки; их не нужно импортировать как пользовательские решения. Каталог исключён из Git, Docker build context и ESLint.

После стенда выполняются reset копии и teardown namespace (для Kubernetes), затем `down` со всеми profiles (`--profile "*"`), чтобы убрать и сети одноразовых verify/reset из профиля tools. У учебного сервера сброс — удаление контейнера. Именованные тома обычных Compose-стендов удаляются вместе с тестовым проектом. В конце удаляются тестовый кластер, служебный compose, принадлежащий прогону том и аренда. Сеть `kind` удаляется, только если её не было до запуска и она пуста; используемая другим кластером сеть сохраняется. Образы остаются в кэше Docker.

`Ctrl+C` / SIGTERM останавливает команду и запускает очистку. Таймаут каждой Docker-команды — 5 минут; очистка не использует отменённый сигнал. Каждый Compose one-off получает известное runner имя. Если CLI отменён или превысил таймаут, runner проверяет метки владельца, проекта и one-off и удаляет только этот контейнер до teardown: иначе он может продолжать скачивание и удерживать flock кластера. При несовпадении меток контейнер сохраняется, а ошибка очистки попадает в summary. Ошибка очистки возвращает ненулевой код и сохраняет `work/` с compose для диагностики. SIGKILL, авария Docker или выключение компьютера не позволяют гарантировать очистку.

Если остались ресурсы, изучите последние `summary.json` и `commands.log`, убедитесь, что runner уже остановлен. В сохранённом `work/` и логе есть точные compose-файлы и команды. Останавливайте только тестовые проекты и удаляйте только кластер `homeops-regression`, его kubeconfig и аренду. **Не удаляйте `homeops` и `homeops-k8s-kubeconfig`.** Флага `--force` для удаления чужих ресурсов нет.

## Расширение

Контрольные исправления и ожидаемые проверки — в `incidentCases.ts`, `composeCases.ts`, `linuxCases.ts`, `namespaceCases.ts`, `nodeCases.ts`, `batch6Cases.ts`, `batch7Cases.ts`, `gpuCases.ts`, `batch10Cases.ts`. Поддерживаются `kind: k8s` (по умолчанию), `server`, `compose`, отдельный жизненный цикл nodeAccess. У стадии возможны фиксированные команды, точечные правки/новые файлы внутри копии, настройки сервисов и список запуска; `workspaceReset` пересоздаёт только рабочее место на прежних узлах, `messageIncludes` проверяет конкретный симптом. `teardownObjects` контролирует отсутствие объектов уровня кластера после teardown, `offline` отключает сеть у всех контейнеров CI; это код разработчика, не пользовательский API. При изменении стенда проверяйте все три состояния и обходы, а не ослабляйте ожидаемые проверки ради зелёного результата.

`npm run check` проверяет контрольные сценарии и жизненный цикл с подменённым Docker. Реальный автопрогон запускается отдельно и не входит в обычную сборку дашборда.
