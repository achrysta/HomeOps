# Windows и WSL2: подготовка к GPU-практике

Машина с Windows 11 и видеокартой NVIDIA на 8 ГБ нужна для лабораторных с vLLM и GPU. Дашборд можно держать там же или на другой машине: прогресс переносится экспортом.

Проект и команды держите внутри WSL. Для GPU-практики заранее подготовьте образы и локальный кэш закреплённых моделей.

## 1. Что установить

1. **Драйвер NVIDIA — в Windows**, свежий (Game Ready или Studio) с nvidia.com. Внутрь WSL драйвер не ставят: WSL получает GPU через драйвер Windows.
2. **WSL2 с Ubuntu** — PowerShell от администратора:
   ```powershell
   wsl --install -d Ubuntu-24.04
   wsl --update
   ```
   Перезагрузка, затем создайте пользователя Ubuntu при первом запуске.
3. **Docker Desktop**:
   - Settings → General → «Use the WSL 2 based engine»;
   - Settings → Resources → WSL integration → включить Ubuntu-24.04.
   GPU в контейнерах Docker Desktop даёт сам, через WSL2 — отдельный NVIDIA Container Toolkit нужен, только если ставить Docker Engine прямо в WSL без Docker Desktop.
4. **Git** — в терминале Ubuntu: `sudo apt update && sudo apt install -y git`.

## 2. Проверки (в терминале Ubuntu)

| Команда | Что должно быть |
| --- | --- |
| `nvidia-smi` | Видна ваша видеокарта и версия драйвера |
| `docker run --rm --gpus all nvidia/cuda:12.8.1-base-ubuntu24.04 nvidia-smi` | Та же таблица — изнутри контейнера |
| `docker info --format '{{.OperatingSystem}}'` | Docker Desktop |
| `free -g` | Памяти WSL хватает: по умолчанию ей отдаётся половина памяти Windows |

Если `nvidia-smi` в контейнере пишет об ошибке — обновите драйвер NVIDIA и Docker Desktop и перезапустите WSL (`wsl --shutdown` в PowerShell).

## 3. Проект в WSL

В терминале Ubuntu:
```bash
git clone https://github.com/achrysta/HomeOps.git ~/HomeOps
```

Проект держите **внутри WSL** (`~/HomeOps`), а не в `/mnt/c/…`: так быстро работают bind mount и правильно определяются пути у сервиса стендов. Инструменты, которые правят проект, тоже запускайте в этой папке внутри WSL, а не в копии на диске `C:`. Окончания строк закреплены в `.gitattributes` (LF), поэтому скрипты стендов не ломаются, даже если клонировать из Windows. Папка `data/` с прогрессом в Git не входит: на новой машине прогресс начинается с нуля, перенести его можно экспортом и импортом на «Резервной копии».

## 4. Запуск

```bash
cd ~/HomeOps
# Первый пользователь свежей Ubuntu имеет UID 1000 — как node в контейнере дашборда.
# Создайте каталог сами: отсутствующий bind mount Docker создаёт от root.
mkdir -p data
docker compose up -d --build
curl -s localhost:8080/healthz
```

Дашборд откроется в браузере Windows на http://localhost:8080. Если дашборд с вашим прогрессом работает на другой машине, решённый здесь инцидент переносится файлом: `incidents/<стенд>/.reports/last.json` → блок «Проверка» в карточке инцидента → «Отчёт из файла».

## 5. Если Docker Hub недоступен

Загрузка образов с Docker Hub иногда обрывается. Достаточно один раз скачать образы там, где Docker Hub доступен, — дальше они берутся из локального кэша:
- `node:24-alpine`, `python:3.12-slim`, `python:3.12-alpine` — дашборд, сервис стендов и стенды;
- `kindest/node` и `kindest/haproxy` — кластер Kubernetes-стендов (скачаются при первом запуске Kubernetes-стенда);
- `nvidia/cuda:12.8.1-base-ubuntu24.04` и образы vLLM — для GPU-лабораторных.

## Ограничения платформы

- **Права bind mount:** отсутствующий `data` Docker создаёт с владельцем `root:root` и правами `755`; `node` в дашборде работает с UID 1000. До первого запуска выполнить `mkdir -p data` под первым пользователем Ubuntu. При другом UID отдельно дайте UID 1000 право записи. Исправлять владельца только каталога проекта; не использовать `chmod 777`, не удалять и не перезаписывать данные.
- **systemd:** `homeops-linux-server` использует `cgroup: private`, `SYS_ADMIN` и `homeops-init` с перемонтированием cgroup2 на запись. Монтирование `/sys/fs/cgroup` хоста вызывает код выхода 255 при создании `init.scope`; полный `privileged` не добавлять. После обновления пересобрать образ сервера.
- **Containerd:** `kind load docker-image` импортирует отсутствующие чужие платформы и падает. `homeops-cluster` использует `docker save --platform linux/amd64` и `ctr import`. Образы для запуска и чарты готовить заранее.
- **Холодный кэш:** команда Docker в автопрогоне ограничена 5 минутами; скачивание может быть дольше. Сначала подготовить образы и веса, затем запускать прогон. Отмена CLI сама не убирает одноразовый контейнер: раннер проверяет метки владельца, проекта и одноразовости, удаляет свой служебный контейнер до `teardown`, иначе он держит `flock`.
- **Сеть:** при EOF от dl.k8s.io — локальная сборка официальных бинарников после проверки SHA, см. `AGENTS.md`. Кэш моделей и образов сохранять.
- **Inference без сети:** локальная модель и закреплённая ревизия, `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, внутренняя сеть; в образе vLLM команда — `python3`. Реальные веса исключены из контекста сборки и тестовых фикстур, служебный CPU-контейнер не видит `/gpu/models`.
- **Бюджет CUDA:** после инициализации свободно около 6,93 ГиБ из 8, хотя занятая память NVML мала. `util 0.90` требует 7,2 ГиБ и отклоняется **до загрузки весов**, не доказывает OOM. Подтверждены 0.5B BF16 с 8K, 4 запросами и `util 0.35`, а также 3B BF16 и 7B AWQ с 8K, 2 запросами и `util 0.85`; режим eager, batch 512. Отказ 3B с 32K при 0.85 — отдельная проверка KV (доступно 0,83 ГиБ, нужно 1,12); 24288 токенов — оценка движка, не прогнанный профиль. [Полный протокол и команды](scripts/models/README.md).
- **Kind и GPU:** физическая RTX не появляется в `allocatable` автоматически; запрос GPU в `gym-ml-platform` проверяется по спецификации, `Pending` ожидаем. HPA без адаптера `model_queue` — диагностика, не работающее автомасштабирование; MLflow-зал — учебные run и registry без обучения.

NVIDIA RTX 4060, 8188 МиБ; Windows KMD 617.42, WSL UMD 615.78.05, CUDA 13.4; vLLM 0.31.0, PyTorch 2.13.0+cu130, Transformers 5.17.0. Исходная память NVML — 10 МиБ.

Проверены amd64-сборки дашборда и сервиса стендов, `/healthz` на локальных портах 8080 и 8091, пути bind mount в WSL, WebSocket и `host.docker.internal`. Linux: `up`, `reset`, `down` пересоздают systemd-сервер; стенды уровня namespace и кластера работают. ## Постоянный служебный контейнер GPU

Проба NVIDIA фиксированная, 20 с; таймаут не кэшируется как «нет GPU». При локальном образе CUDA новая проба после простоя заняла 1,029 с, повтор — 0,716 с; запуск GPU-стенда — 2,118 с, повтор — 5,369 с, включая Compose и сборку. Живая проверка читает только runtime, health и ограничения; настоящий inference — только полный автопрогон с `DASHBOARD_URL=off`.

Замер 11 октября 2026: первый опрос после `up` с прогретыми образами и весами; 20 последовательных и 5 параллельных запросов в сломанном и исправленном состояниях. Время HTTP измерено до полного JSON; p50 — медиана, p95 — ближайший ранг `ceil(0.95*n)`. RAM — занятая память служебного контейнера без кэша файловой системы, **не VRAM**.

| Стенд / состояние | Первый, с | Тёплый p50/p95, с | Параллельный, с | RAM, МиБ | Контейнеры |
| --- | ---: | ---: | ---: | ---: | --- |
| `gpu-lora` / сломано | 0,732 | 0,736/0,812 | 1,534 | 1,961 | 3→3 |
| `gpu-lora` / исправлено | 0,661 | 0,691/0,708 | 0,695 | 2,023 | 3→3 |
| `gpu-vllm-budget` / сломано | 0,768 | 0,743/0,787 | 0,725 | 2,336 | 3→3 |
| `gpu-vllm-budget` / исправлено | 0,677 | 0,703/0,756 | 0,720 | 2,301 | 3→3 |

ID контейнеров `model`, `gateway`, `live` неизменны; пять запросов получают один JSON с одинаковым `at`. События Docker не содержат `create` при опросе (только при `up` и `reset`). После `reset` проба GPU может ещё быть красной и закрывать `ready` через `needs` — это не общий ответ 409 «нет GPU». Сброс `gpu-container` сохраняет служебный контейнер из канонического `.original/compose`. Его `/gpu/models` скрыт пустым `tmpfs` только на чтение; модель читает свой `/models`. `reset` возвращает сломанное состояние, `down` удаляет контейнеры.
